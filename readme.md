# Amazon Payment Services plugin for WooCommerce
<a href="https://paymentservices.amazon.com/" target="_blank">Amazon Payment Services</a> plugin offers seamless payments for WooCommerce platform merchants.  If you don't have an APS account click [here](https://paymentservices.amazon.com/) to sign up for Amazon Payment Services account.


## Getting Started
We know that payment processing is critical to your business. With this plugin we aim to increase your payment processing capabilities. Do you have a business-critical questions? View our quick reference [documentation](https://paymentservices.amazon.com/docs/EN/index.html) for key insights covering payment acceptance, integration, and reporting.


## Configuration and User Guide
You can download the archive [file](/woocommerce-aps.zip) of the plugin and easily install it via WordPress admin screen.
WooCommerce Plugin user guide is included in the repository [here](/Woocommerce%20Plugin%20User%20Guide.pdf)

## Compatibility with other WooCommerce extensions

APS WooCommerce plugin is compatible with below existing WooCommerce extensions. Extension names are mentioned as they are available in Wordpress marketplace.

  * Multi Currency for WooCommerce : Allows to display prices and accept payments in multiple currencies. APS plugin has a setting to use Front(Currency selected by user) / Base(Currency selected in WooCommerce settings)
  * Woocommerce one page checkout and layouts : One page checkout layout for WooCommerce. This plugin shortens the checkout flow by merging cart, billing, shipping and payment steps in one page.
  * WooCommerce Subscriptions : Plugin to enable recurring payments functionality. Products will be configured as subscriptions.
  * WPML Multilingual CMS : Plugin for supporting multiple languages. APS Plugin currently supports Arabic and English

## Apple Pay certificate storage
Apple Pay merchant certificates and private keys are never kept in a web-served directory (`uploads`, `wp-content`, the plugin folder or the document root). The plugin stores them as raw PEM files (mode `0600`, directory `0700`, random names) in `aps-private-certificates/` next to the document root, or in the directory you set in `wp-config.php`:

```php
define( 'APS_CERTIFICATES_DIR', '/var/lib/aps-certificates' ); // absolute, outside the web root
```

* The directory is checked against the canonical (symlink-resolved) path of the document root, `ABSPATH`, `wp-content`, plugins, uploads and themes. Anything inside them is rejected. If your web server serves another location, add it with the `aps_certificate_web_roots` filter.
* There is no fallback. If no safe directory exists, or a file cannot be migrated, Apple Pay is switched off and an administrator notice explains why.
* **Permissions are verified before every write and use:** the directory must be owned by the web server user with no group/other access (`0700`), stored files and the `.aps-site` marker likewise (`0600`). The mode is re-read after each `chmod`; a `chmod` that fails or is ignored by the filesystem keeps Apple Pay off. The plugin tightens only the directory it created itself (`aps-private-certificates`) and files inside it; a directory you set with `APS_CERTIFICATES_DIR` is never `chmod`-ed (it may be shared), so run `chmod 700` on it yourself (`dir_permissions` until then). Ownership is compared with the PHP process uid, so the PHP `posix` extension must be enabled; without it, and on Windows, owner/mode cannot be verified and Apple Pay stays off (`permissions_unverifiable`, nothing is created).
* **Several web servers or containers:** set `APS_CERTIFICATES_DIR` on every node to the same shared, persistent mount (for example EFS/NFS with hard-link support). A node that does not see the directory reports an error; it never creates a different one. Local container storage is lost on redeploy.
* **Multisite:** each site uses a `site-<id>` sub-directory.
* Files from earlier versions (`uploads/aps-certificates`, `wp-content/aps-private-*`, a previously pinned directory) are moved in when an administrator opens wp-admin. A source file is deleted only after the copy was read back and compared; on a conflict or failure it is kept and the error stays visible.
  * Every PEM file in the plugin's own old folders is moved, referenced or not; one whose name is invalid or already taken is stored under a new random name (an identical stored copy is reused). Non-PEM files are left alone (warning). In a previously pinned web-served directory only `*.crt.pem` / `*.key.pem` files (and their `.php` guarded variants) are treated as the plugin's; other files there are never read or deleted. On multisite an unreferenced file in such a shared directory is not moved, as it may belong to another site.
  * **Any leftover in a web-served location that may hold key material blocks Apple Pay until it is gone**, including after a repair upload: an unreadable folder or file, a symlink, a file that cannot be deleted, or an unmoved shared file. The plugin cannot make a file it cannot delete unreachable for the web server, so remove such files manually (the notice says so), then open wp-admin again.
* **Ownership marker:** the certificate directory contains a `.aps-site` file with a hash of the site URL, written the first time an administrator opens wp-admin (until then the directory is not used). A staging/cloned copy of the configuration that points at another site's directory sees a different marker and neither reads, writes nor deletes anything (`dir_site_mismatch`). The automatic pin is bound to the site URL the same way (`pin_site_mismatch`).
* **Recovery after a deliberate site URL/domain change (or any `pin_site_mismatch` / `dir_site_mismatch`):** Apple Pay stays off (fail closed). Ownership is never taken over automatically and there is no override constant. Create a NEW, separate directory outside the web root, set `APS_CERTIFICATES_DIR` to it, open wp-admin once as an administrator (the directory is claimed for the new URL) and upload the matching Apple Pay certificate and key again. The old directory is left untouched.
* **Limitation:** a site's identity is its URL stored in the database. A clone of the database that keeps the same URL (for example a staging copy that was not renamed) cannot be told apart from production, so every environment must have its own storage: never mount production's certificate directory on a staging or test environment.
* **Legacy key cleanup:** after successful re-upload, review any PEM files left in `uploads/aps-certificates`, `wp-content/aps-private-*`, the old directory after a site URL change, and backups. Remove unneeded copies manually only after checking the active certificate and key. If a key may have been web-accessible, revoke and reissue the Apple Pay credentials with the provider.
* Uploads require an administrator (`manage_woocommerce`), a matching certificate/private-key pair (checked against the stored counterpart when only one file is uploaded) and a saved setting; superseded files are deleted only after that. A broken configuration (a referenced file is missing) can be repaired by uploading a new pair.
* WP-CLI/cron started from the command line never creates, migrates or deletes anything unless `APS_CERTIFICATES_ALLOW_CLI_MIGRATION` is defined as `true`.
